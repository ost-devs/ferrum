Precedents moved out of the index to keep it short. Each points at its record; re-check before relying on one.

- A field of a fixture output that Ferrum cannot compare (a source line, a stack): ask who it was for; if it links evidence for the specification's reader, move the link into the tool (computed beside the run, for every case, checked against the rows) and keep the output to what the caller observes. Prototype on all chunks first (26 hand-recorded sites became 355 checked). `docs/decisions/ferrum-state.md` Q59
- Which fixtures a deviation leaves out: never list by reading. Write the deviation into the harness copy of cm6, replay everything, take what changes, restore (diff clean). Two minutes gave 170 fixtures for one row where reading had found 1. `docs/decisions/ferrum-state.md`, "S5, second part"
- "Replayed or not" is the wrong unit: leave out the call that has no counterpart, compare the rest; whole-fixture exclusion would have dropped the 160 cluster fixtures. What only the Rust signatures decide (type exclusion) is frozen in a file after the replayer's first run and approved by reason. Same entry
- Identity of cm6 objects: model program-built JS objects as references whose `PartialEq` is by pointer (D14), so user values replay exactly through the public API; compare identity of Ferrum values only where a caller or a performance target depends on it (definitions, slots read from a state, `Text` nodes, chunks, states). Measure which operand types the fixtures compare before writing the rule. Same entry
- A check on a file only I write must not fail a worker's run: count it, and require zero at approval. `docs/decisions/method.md`, 2026-11-14
- String-keyed dynamic protocol of cm6 (language data): ask what the names buy (crates that provide without importing the reader) before typing it away. Same ferrum-state entry
- Figures in a record: recompute each from the tool output before committing (three of mine were wrong in the draft).
- Facts I did not all verify (314 position rows): accept them when a wrong one cannot pass silently (it fails a fixture), say which I checked, and never when the error would hide. Same entry
- When one program is the proof (a replayer), plan around its false passes: a control run on altered expected values, an approved file of what it leaves out, unwritten code never counted as a matching error. Same entry
- A check may change after its code without a call per fix: its author fixes it, each fix names the rule it restores, I read the list in batches; a fix that restores no rule is a question. Same entry
- Prose marks that a later reader must interpret (positions without their text): make the author write the fact as a row with the op; reading them afterwards cost a run and found 32 gaps. `docs/decisions/method.md`, 2026-11-14, end of stage
- A document that names paths the work will create declares them (`refs:planned`), so the checker stays strict on every other path and the marker goes stale by itself. Same entry
- A number inside a formatted string of cm6 (an error message, a debug form) is a position like any other: compare it converted, never stripped; state the text per cm6 throw (the function owns it), not per harness op, and let the replayer find it by the argument the message repeats; ambiguity is a question, never "any text that fits". Before deciding, run the fixtures with a wrapper that tallies op by throw site. `docs/decisions/ferrum-state.md` Q60
- Tool or agent for a step: ask what the step is for, then whether data determine its answer (tool), whether they would if the producer wrote a fact instead of prose (move structure upstream), whether many instances of one shape have two readers (small language), else agent with a tool around it. Generate from a declaration, never from code or prose. `docs/workflow/evolution.md` §4; `docs/decisions/method.md`, 2026-11-14, "Each kind of work"
- A maintainer idea that the plan already contains: say so, then ask the same question of every neighbouring piece; that is where its value was (evaluator without a run-made reference, triage by argument, checks composed by hand). Same entry
- The proof's own tool needs expected values from a run too (language cases from `program.ts`), and a triage tool before a check-fix loop starts, not after it fails to converge. Same entry
- Approving signatures (a skeleton): read each against how cm6's callers write the call (count the call forms in the mirror), not against the declaration alone; compile every form before deciding it. A TS type guard (`is`) becomes a typed read, a flag that makes the result absent becomes two functions, a callback that never outlives its call takes no thread bounds. `docs/decisions/ferrum-state.md`, "The skeleton approved"
- A property the Rust type cannot hold (member order of a JSON object): do not rebuild it with a dependency feature that only tests turn on; promise nothing, and make the proof compare what the type does hold. Same entry
- A tool's "accepted, and listed for the consultant" is a hole when the list can contain what the plan says needs a check: make the exemption a fact of the row (its class). Same entry
- Where a rule of mine (D14) leaves Ferrum below cm6 for the developer, that is an improvement row too, with the point at which counts decide it.
- A hand-written list of what a proof leaves out (fixtures under a row): list only what the tool cannot find itself, and make the run check the list (a listed case that equals its record fails). Reading the listed cases one by one found a third of them redundant, some siblings missing and one reproduced. `docs/decisions/ferrum-state.md`, "Q75 to Q78"
- Rules a proof tool follows only on values the reference never produces ("no counterpart") have no run-made reference: require literal tests of each rule, and a named reason per rule in the report so the cautious choices can be counted before they are loosened. Same entry
- A shortcut in an evaluator (not evaluating the arguments of an op whose result is discarded) is judged by what reads its trace, not by the result alone. Same entry
- A proof's result names ("compared in part") must not be earned by shape alone: a case with no compared value is "not compared", while its shape still fails on a difference. Report less than is checked, never more. `docs/decisions/ferrum-state.md`, "Q79 to Q83"
- Work split by unit when the data are split by chunk: the piece belongs to where its definition lives (the chunk's interpreter), and the worker who later holds the rules re-reads what was bound early. Same entry
- `impl Trait` returned from `&self` (edition 2024) borrows the receiver unless `use<>`; compile every "outlives" claim of a signature. Same entry
- A draft left by a cut run is a claim: re-derive each part; its arithmetic and its citations were where it erred (a budget rule stated and not applied; a test-writer choice called "cm6's code" when it only follows from it). `docs/decisions/ferrum-state.md` "The pilot review of the implementation"
- What is determined by the report (a behavior with nothing compared, a test file's unit) is classified by the tool and the printed list read, never a hand-written list of rows. Same entry
- A precondition on an argument fails on the argument alone (tab size 0), not when the data first trigger it. Same entry
- A JS `1e9` meaning "to the end" that no output shows is no bound; reproducing a hang is never parity (D11 a). Run the hang and a patched cm6 for the reference before deciding. `docs/decisions/ferrum-state.md` "Q92 and Q93"
- A check that fires at the code step on something the data fix before code (rows list fixtures, fixtures name behaviors) belongs at the checks step as a tool check; try it on the real miss and a seeded one. Same entry
- An implementer's list of "cases with no row" is triaged by me before a spec-auditor runs: re-derive reachability from every writer of the data (Q94: the `change.ts:388` case was unreachable). A flag on a row is a key on that row, aimed at whoever must read it (`added` → conformance). `docs/decisions/ferrum-state.md` Q94.
- A card of a round after a unit's code must not ask a pre-code check (`checks <unit>`); my own Q92/Q93 text did. Check each check I name against the state it will run in. Q94.
- A fact written twice in the data (row `fixtures` and fixture `behaviors`) is checked both ways by a tool; a card's "no X is added" must not forbid the edit that keeps such a link whole (`docs/decisions/ferrum-state.md`, "Step 3 of U3 read").
- A replayer's reason `type` is read against D12 at approval: when a worker files under it a value cm6 handles by a language rule (truthiness, absence), a call Ferrum's form moves to the caller (no field to merge), or reflection on a JS object, give each the reason its reader can check (D12 widened, a `replay.jsonl` row), and verify an equivalence claim by patching the harness's cm6 (unwrap `{extension}`, swap combineConfig's loops) over every chunk. `docs/decisions/ferrum-state.md` "Q105 to Q110"
- A form that moves a loop of cm6 into the caller (per-field merge) may change which of several true errors is reported: keep the form, list the computed fixtures under a `form` row, and put a `cm6 deviation` line where the crates above will read it. Same entry
- Approving a left-out file or widening a rule like D12: group every entry by chunk, op and argument with its distinct values and read each group against the code that reads it; "I read every site" from memory missed two (Q109). A tool's count line ("99 of 143") is re-derived before acting on a summary of it. `docs/decisions/ferrum-state.md`, "The end of the implementation stage"
- A language rule callers rely on (truthiness, absence, a primitive's conversion to a string) is applied as its result; an object's conversion is not (it calls methods). Same entry; D12
- Before deciding a rule a tool will check, run it against every case the check covers (cm6's traces of all 143: 30 seconds); a rule generalized from the failing cases was wrong for 26. A label the producer cannot compute is dropped, not guessed; the tool that sees the truth prints it. `docs/decisions/ferrum-state.md`, "Q120, the line `Line::is_empty`, and branch coverage"
- A check is never chosen or replaced because the environment lacks a tool: ask the maintainer for it, then weigh it on what it shows. Line, branch and mutation coverage answer different questions (not run, condition never true/false, change not forbidden); none stands for another. Run it before deciding. Same entry
- A code step's mismatches are mostly the proof's own: sort them by class, re-derive each from fixture + cm6 + the rule named, and run the replayer after a row change before trusting it. A row list made by reading, or computed on one chunk only, is wrong both ways (F0179 listed and reproduced; F0477 unlisted); find a row's class of inputs by scanning the fixtures, never by recall. `docs/decisions/ferrum-state.md` "Q116 to Q118"
- A value of an any-typed slot (language data) is stored as given; a JS `null`/`undefined` there is a program value, not D12's absent, unless cm6 tests it as absent. A rule list that names "cases 1 to 4" must be checked against every case that shares the reason (case 5). Same entry
- A behavior that is only object identity of a type Ferrum makes a value: a written test of the value counterpart, not a form row; a behavior of another package (the view's keymap): a form row naming where it is checked. Same entry
- A listed "case with no row" is settled by a patched-cm6 run (pinned or not), then a probe program on both copies for observability before ordering step 3. Same entry
- Hidden per-call state (a thread-local flag) standing in for a fact the types lose: look for a reentrant path, then make the fact part of the value; compile in scratch first; keep D6 whole. `docs/decisions/ferrum-state.md` "Q119 and what remains after U4"
